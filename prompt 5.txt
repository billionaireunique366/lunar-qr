1. DIAGNÓSTICO PRIMEIRO (antes de mudar)
Diz-me qual é a causa provável da falha actual. Verifica:
- que valor tem AUDIO_URL agora (caminho local? file://? link do Dropbox com dl=0?);
- se o objecto Audio tem crossOrigin definido, ou se o áudio passa pela Web Audio API (AudioContext / createMediaElementSource). O Dropbox não garante cabeçalhos CORS, e qualquer uma das duas coisas pode deixar o áudio mudo no telemóvel;
- se o audio.play() é chamado directamente dentro do handler do toque, sem await, setTimeout ou fetch antes;
- se o caminho tem diferenças de maiúsculas/minúsculas (.MP3 vs .mp3). O servidor de hospedagem diferencia, o Windows não.

- Se o primeiro der erro (evento "error" no Audio), tenta automaticamente o FALLBACK uma vez, no mesmo objecto Audio (trocar o src e voltar a chamar play()). Só depois de os dois falharem é que o player mostra "Áudio indisponível".

3. REGRAS PARA O ÁUDIO FUNCIONAR NO TELEMÓVEL
- NÃO definir crossOrigin no Audio.
- NÃO usar Web Audio API / AudioContext. O equalizador do player continua a ser só animação CSS enquanto o áudio toca, sem análise real do som.
- audio.play() chamado directamente no handler do toque do botão da pré-página, de forma síncrona, com .catch() na promise.
- Se o play() for rejeitado (NotAllowedError), o player fica em pausa com pulso para a pessoa tocar outra vez. O formulário aparece sempre.
- preload="auto" na pré-página, como já está.

4. MODO DIAGNÓSTICO NO ECRÃ (?debug=1)
No telemóvel não há consola, por isso preciso de ver o erro no próprio ecrã. Com ?debug=1 no URL, mostra uma caixinha fixa no fundo do ecrã (texto pequeno, fundo preto semi-transparente) com:
- o src em uso (curto: "directo" ou "fallback");
- os eventos do áudio à medida que acontecem: loadstart, loadedmetadata, canplay, playing, waiting, stalled, error;
- em caso de error: audio.error.code e audio.error.message;
- em caso de play() rejeitado: o nome e a mensagem do erro;
- o audio.readyState e o audio.networkState actuais.
Sem ?debug=1, nada disto aparece nem pesa.
